## 1. Descripción del alcance

Este pase incorpora la parametrización de la ruta de archivos de log del sistema. La ruta y la retención de logs dejan de estar fijas en el código y pasan a ser configurables desde `appsettings.json`, sin necesidad de recompilar la aplicación.

### Cambios incluidos

| Componente | Tipo de cambio | Descripción |
|---|---|---|
| Binarios de la aplicación | Actualización | Se reemplazan los DLL compilados con el build de este alcance |
| `appsettings.json` | Configuración nueva | Se agrega la sección `SerilogSettings` con la ruta de logs y días de retención.  Se agrega la sección `DataProtection` con la ruta de almacenamiento de keys |
| `Program.cs` | Corrección | Se agrega configuración de Data Protection para persistir keys de antiforgery en disco |

### Archivos entregados

| Archivo | Contenido |
|---|---|
| `datahub_alcace_1.zip` | Binarios compilados de la aplicación |

## 5. Actualizar appsettings.json

Este paso agrega la nueva sección de configuración de logs al archivo existente. **No reemplaza el archivo completo.**

### 5.1 Abrir el archivo de configuración

```powershell
notepad "C:\Sitios\DataSmartHub\appsettings.json"
```

### 5.2 Agregar la sección SerilogSettings

Localice la llave `"AllowedHosts"` en el archivo. Agregue el bloque siguiente **inmediatamente después** de esa propiedad, antes del cierre del JSON:

```json
"SerilogSettings": {
  "LogPath": "Logs/log-SDH-.txt",
  "RetainedFileCountLimit": 30
}
```

**Ejemplo de la sección en contexto dentro del archivo:**

```json
{
  "ConnectionStrings": {
    "DefaultConnection": "ENC:..."
  },
  "Logging": { ... },
  "AllowedHosts": "*",
  "SerilogSettings": {
    "LogPath": "Logs/log-.txt",
    "RetainedFileCountLimit": 30
  },
  "JwtSettings": { ... },
  ...
}
```

| Propiedad | Descripción | Valor recomendado producción |
|---|---|---|
| `LogPath` | Ruta y nombre del archivo de log. Acepta ruta relativa o absoluta. | `"Logs/log-SDH-.txt"` (relativa a la raíz del sitio) |
| `RetainedFileCountLimit` | Cantidad de archivos de log diarios que se conservan. | `30` |

**Personalizar el nombre del archivo de log:**

El nombre del archivo se puede ajustar segun el estandar de nombrado de la organizacion. Serilog agrega automaticamente la fecha al nombre antes de la extension. El prefijo antes del guion final es la parte configurable:

```
"LogPath": "Logs/<prefijo>-.txt"
                   ^^^^^^^^
                   Esta parte se personaliza
```

Ejemplos segun convenciones comunes:

| Estandar | Valor de LogPath | Archivo generado |
|---|---|---|
| Por aplicacion | `"Logs/log-SDH-.txt"` | `log-SDH-20260618.txt` |
| Por sistema | `"Logs/DataSmartHub-.txt"` | `DataSmartHub-20260618.txt` |
| Generico | `"Logs/log-.txt"` | `log-20260618.txt` |

**Ruta relativa** — los logs se generan dentro de la carpeta del sitio:
```
C:\Sitios\DataSmartHub\Logs\log-SDH-20260618.txt
```

**Ruta absoluta** — ejemplo si se requiere centralizar logs fuera del sitio:
```json
"LogPath": "D:/Logs/DataSmartHub/log-SDH-.txt"
```

> **Nota:** En el ambiente de produccion los grupos ya se encuentran actualizados con los nombres nuevos. Esta seccion aplica unicamente al ambiente de certificacion.

  "AGENTE": "G_DSH_USER",

**Valor nuevo (certificacion):**

  "SUPERVISOR": "GS_DSH_SUPERVISOR",

### 5.4 Agregar la seccion DataProtection

Localice la sección `"SeedSettings"` en el archivo. Agregue el bloque siguiente **inmediatamente antes** de `"LdapSettings"`:

```json
"DataProtection": {
  "KeysPath": "DataProtection-Keys"
}
```

**Ejemplo de la sección en contexto dentro del archivo:**

```json
{
  ...
  "SeedSettings": { ... },
  "DataProtection": {
    "KeysPath": "DataProtection-Keys"
  },
  "LdapSettings": { ... }
}
```

| Propiedad | Descripción | Valor recomendado producción |
|---|---|---|
| `KeysPath` | Ruta donde se persisten las keys de Data Protection. Acepta ruta relativa o absoluta. | `"DataProtection-Keys"` (relativa a la raíz del sitio) |

**Ruta relativa** — las keys se almacenan dentro de la carpeta del sitio:
```
C:\Sitios\DataSmartHub\DataProtection-Keys\
```

**Ruta absoluta** — ejemplo si se requiere centralizar fuera del sitio:
```json
"KeysPath": "D:/DataProtection/SmartDataHub"
```

> **Importante:** La carpeta se crea automaticamente si no existe. Esta carpeta **no debe eliminarse** entre deployments. Si se elimina, los tokens de antiforgery y cookies activas se invalidan y los usuarios deberan iniciar sesion nuevamente.

### 5.5 Actualizar el nombre de la base de datos en la cadena de conexión

> **Aplica solo al ambiente de certificación (BQA).** La cadena de conexión actual apunta a `DB_ODS_DEV1`. Debe actualizarse a `DB_ODS_STG` antes de iniciar el sitio.

La propiedad a modificar es `Database=` dentro de `ConnectionStrings:DefaultConnection`.

**Si la cadena de conexión está en texto plano**, edite directamente el valor en `appsettings.json`:

```json
"ConnectionStrings": {
  "DefaultConnection": "Server=<servidor>;Database=DB_ODS_STG;..."
}
```

**Si la cadena de conexión está cifrada** (`ENC:...`), el texto plano no es editable directamente. Use el **SmartHub Secret Tool** para generar un nuevo valor cifrado:

1. Obtenga el texto plano de la cadena de conexión actual (desde documentación interna o el equipo responsable del ambiente).

2. Modifique únicamente el segmento `Database=DB_ODS_DEV1` reemplazándolo por `Database=DB_ODS_STG`. Deje el resto de la cadena sin cambios.

3. Ejecute el SecretTool en el servidor de certificación:

   ```cmd
   SDH.SecretTool.exe
   ```

   Verifique que la herramienta muestre `CONFIG_MASTER_KEY: *** [OK]` antes de continuar.

4. Seleccione la opción **1 — Cifrar cadena** e ingrese la cadena de conexión completa con el nombre de base de datos correcto:

   ```
   Seleccione una opcion: 1
   Ingrese el valor a cifrar: Server=<servidor>;Database=DB_ODS_STG;Integrated Security=True;...
   ```

5. Copie el valor resultante (con prefijo `ENC:`) y reemplácelo en `appsettings.json`:

   ```json
   "ConnectionStrings": {
     "DefaultConnection": "ENC:<nuevo_valor_cifrado>"
   }
   ```

> **Importante:** El valor cifrado cambia cada vez que se cifra aunque el texto plano sea idéntico. Esto es normal — AES-256-CBC usa un IV aleatorio. El valor es válido mientras `CONFIG_MASTER_KEY` sea la misma que usa la aplicación.

### 5.6 Validar el JSON

Antes de guardar, verifique que el archivo JSON es válido. Puede pegarlo en un validador en línea o ejecutar desde PowerShell:

```powershell
Get-Content "C:\Sitios\DataSmartHub\appsettings.json" | ConvertFrom-Json
```

Si el comando no lanza error, el JSON es válido. Guarde y cierre el archivo.

## 9. Recrear base de datos y cargar datos de prueba

Este procedimiento elimina la base de datos actual, la vuelve a crear vacía y luego arranca la aplicación, que aplica automáticamente todas las migraciones y carga los datos iniciales de prueba.

> **Alcance:** Ambiente de certificación (BQA). No ejecutar en producción.

### 9.1 Detener el sitio en IIS

Antes de manipular la base de datos, detenga el sitio para evitar conexiones activas durante el drop.

```powershell
Stop-WebSite -Name "Data Smart Hub"
Stop-WebAppPool -Name "SmartHubPool"
```

Verifique que no queden conexiones abiertas al motor SQL:

```sql
-- Ejecutar en SQL Server Management Studio
SELECT session_id, login_name, status, host_name, program_name
FROM sys.dm_exec_sessions
WHERE database_id = DB_ID('DB_ODS_STG')
  AND session_id <> @@SPID;
```

Si existen sesiones activas, ciérrelas antes de continuar.

### 9.2 Borrar la base de datos actual

> **Precaución:** Esta operación es irreversible. confirmar que se haya sacado un respaldo de la base de datos antes de continuar.

Conéctese a SQL Server con una cuenta con permisos `sysadmin` o `dbcreator` y ejecute:

```sql
USE master;
GO

-- Desconectar sesiones activas y eliminar la base de datos
ALTER DATABASE DB_ODS_STG SET SINGLE_USER WITH ROLLBACK IMMEDIATE;
GO

DROP DATABASE DB_ODS_STG;
GO
```

Confirme que la base fue eliminada:

```sql
SELECT name FROM sys.databases WHERE name = 'DB_ODS_STG';
-- Debe retornar 0 filas
```

### 9.3 Crear la base de datos vacía

Cree una base de datos nueva con el mismo nombre. La aplicación creará todos los esquemas y objetos al arrancar.

```sql
USE master;
GO

CREATE DATABASE DB_ODS_STG;
GO
```

> El nombre `DB_ODS_STG` debe coincidir exactamente con el valor de `Database=` en la cadena de conexión del `appsettings.json` del ambiente.

### 9.4 Iniciar el sitio en IIS

Al arrancar, la aplicación ejecuta automáticamente:

1. `MigrateAsync()` — aplica todas las migraciones de EF Core y crea esquemas, tablas y constraints.
2. `UsuarioSeeder` — inserta usuarios de prueba si la tabla está vacía.
3. `ViewSeeder` — crea o actualiza las vistas de base de datos.
4. `CatalogoSeeder` — carga los catálogos parametrizables iniciales.

```powershell
Start-WebAppPool -Name "SmartHubPool"
Start-WebSite -Name "Data Smart Hub"
```

Espere entre 15 y 30 segundos para que el proceso worker complete la inicialización antes de verificar.

### 9.5 Verificar la migración y el seed

**Verificar que las migraciones fueron aplicadas:**

```sql
USE DB_ODS_STG;
GO

SELECT MigrationId, ProductVersion
FROM dbo.__EFMigrationsHistory

```

Debe aparecer al menos la fila `20260624173938_InitCreate`. Si la tabla está vacía o no existe, la migración no se ejecutó correctamente — revise los logs antes de continuar.

**Verificar que las tablas fueron creadas:**

Las líneas deben mostrar mensajes de inicio y finalización del seed sin errores.

**Verificar acceso funcional:**

- [ ] El sitio responde en el puerto configurado.
- [ ] El dashboard carga sin errores.

### 9.6 Cargar clientes de prueba

> **Requisito previo:** Completar y verificar el paso 9.5 antes de ejecutar este script. Si la migración no fue exitosa, no continuar.

Una vez confirmada la migración exitosa, ejecute el script de clientes de prueba:

```
CI_DB\DB_ODS\Scripts\Insert_Clientes_Prueba.sql
```

Conéctese a `DB_ODS_STG` en SQL Server Management Studio y ejecute el script completo. El script:

1. Resuelve los IDs de catálogos necesarios desde `parametro.Tbl_Cat_Item`.
2. Inserta 3 clientes con identificaciones `1701234567`, `1756789012` y `1798765432`.
3. Carga 4 datos de contacto por cliente (2 celulares y 2 correos).
4. Carga 1 dirección por cliente con datos de georeferenciación (sector, parroquia, coordenadas) correspondientes a Guayaquil.
5. Al finalizar, muestra dos consultas de verificación: contactos y direcciones de los clientes insertados.

> Si el script imprime `Los 3 clientes de prueba ya existen en la base de datos. No se insertó nada.`, la ejecución previa fue exitosa y no es necesario repetirla.

**Verificar la carga:**

```sql
USE DB_ODS_STG;
GO

SELECT c.Identificacion_Cliente, c.Nombre_Completo,
       d.Direccion_Completa, d.Ciudad, d.Parroquia, d.Latitud, d.Longitud
FROM operativo.Tbl_Maest_Cliente c
JOIN operativo.Tbl_Direccion_Cliente d ON c.Id_Cliente = d.Id_Cliente
WHERE c.Identificacion_Cliente IN ('1701234567','1756789012','1798765432');
```

Deben retornar 3 filas, una por cliente, con latitud y longitud distintos de NULL.
